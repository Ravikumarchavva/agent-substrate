# Kernel Audit — 2026-07-02

**Scope:** `src/substrate/kernel/` (all 30 files, 5086 LOC) plus the concrete
L1 implementation that's supposed to honor its contracts
(`agents/runtime/context.py`, `agents/runtime/worker.py`,
`agents/runtime/backends/`, `agents/core/react.py`).

**Goal being audited against:** true stateless operation — every state
change persisted as an event, so a run can be reconstructed and safely
retried from that event history alone. This is the standard an enterprise
deployment needs; the audit checks the kernel against it directly, not
against a vaguer "does it look reasonable" bar.

**Method:** read every kernel runtime contract file in full; traced the
concrete Stage 0 implementation for each one; grepped for claims made only
in docstrings vs. code that actually exists; checked the one place these
guarantees matter most in production (`ReActAgent._react()`) to confirm
whether it actually uses the journaled path or bypasses it. Every finding
below is either a `file:line` citation or a reproducible grep/read — none of
this is from memory of how the system "should" work.

---

## Verdict

**Two different things score very differently, and conflating them is the
main way to misjudge this kernel:**

- **Contracts / design:** genuinely good. The `EventLog`/`Journal`/`Effect`
  design has the right doctrine (fold-is-truth, deterministic effect IDs,
  optimistic concurrency, at-most-once semantics) and it's not just
  decoration — parts of it are real and wired into the production agent loop.
- **What's actually delivered today, against "stateless + safe retry":**
  **not there yet.** The single biggest gap: *suspending a run does not mean
  what the contracts say it means.* No suspension primitive updates the
  Scheduler, so a process crash during any suspension (HITL wait, subagent
  join, timer sleep) is indistinguishable from a genuine crash — and gets
  treated as one, silently losing or duplicating work.

The good news implied by this split: closing the gap is mostly "implement
what's already documented," not "redesign the kernel." The contracts you'd
want to build against are already correct.

## What's done — genuinely solid, with evidence

### `EventLog` — real, correctly specified
[`kernel/runtime/log_entry.py`](../../../src/substrate/kernel/runtime/log_entry.py)
- Explicit doctrine: *"A run's state is `fold(entries from seq=0)`"* (line 8).
- `append()` takes `expected_seq`; mismatches raise `ConcurrentAppendError`
  (`kernel/core/errors.py:92`) — real optimistic-concurrency fencing, not
  just documented.
- Postgres backend exists: `infrastructure/runtime/pg_event_log.py`.

### `Effect`/`Journal` — real, and *actually used in production*
[`kernel/runtime/effects.py`](../../../src/substrate/kernel/runtime/effects.py)
- `Effect.make_id(run_id, step_seq, kind, args)` — deterministic, sorts dict
  keys before hashing so argument order doesn't affect the id (line 63-80).
- `Journal.record()` is documented and implemented as write-once: first
  result wins, never overwritten (line 111-113).
- **Verified this is wired into the real agent loop, not just example code:**
  `agents/core/react.py:161` calls `await ctx.llm(...)`;
  `agents/core/react.py:191` calls `await ctx.tool(tc.tool_name, ...)`. Both
  are the journaled paths in `agents/runtime/context.py` (`llm()` at line
  349, `tool()` at line 456) — both do journal-lookup-before-execute and
  journal-record-after. This is the one part of the enterprise-retry story
  that is real today, not aspirational.
- Redis backend exists: `infrastructure/runtime/redis_journal.py`.

### Layer boundaries — enforced, tested
- Import-linter contracts (`pyproject.toml`) + `tests/architecture/test_kernel_invariants.py`
  actually check import direction (`test_kernel_has_no_upward_imports`), not
  just document it.
- `kernel/` genuinely has zero I/O and zero imports from any layer above it —
  confirmed by the passing invariant test, re-run any time via
  `uv run pytest tests/architecture/test_kernel_invariants.py -q`.

### Durable backends: 4 of 6 built
Postgres: `EventLog`, `Inbox`, `Scheduler`. Redis: `Journal`. All real,
all wired via `infrastructure/runtime/factory.py::build_postgres_runtime()`,
which is what `RUNTIME_BACKEND=postgres` (the default, `config.py:52`)
actually gets you.

## What's broken or just a patch — with evidence

### 1. No `fold`/replay function exists anywhere

```
grep -rn "fold\|Checkpoint" src/substrate/kernel/ src/substrate/agents/
```
returns 6 hits, **all in docstrings/comments, zero implementations**:
- `kernel/runtime/agent.py:9` — *"runtime calls `run` each time the agent
  wakes from SUSPENDED, after folding the EventLog to reconstruct state"*
- `kernel/runtime/supervisor.py:117,173` — *"crash reconciliation: a resumed
  parent folds its log..."*
- `agents/runtime/worker.py:6` — the implementation's own docstring, honestly:
  *"the coroutine is suspended by asyncio, not by the durable serialize/fold
  mechanism (that is Stage 1)"*

**What actually happens on restart:** `Worker._run_agent()` never reads or
folds the EventLog before calling `agent.run(ctx, inbox_msgs)` — it just
drains the inbox and calls `run()` fresh. This *happens* to work reasonably
for `ReActAgent` specifically, because its behavior is entirely re-derivable
from persisted conversation history + the Journal's effect cache (a fresh
call re-issues the same LLM/tool calls in the same order, gets cache hits,
fast-forwards through already-done work). That's a fortunate property of one
agent's design — **it is not a kernel-level guarantee**, and it breaks for
any suspension whose resume state isn't fully captured by conversation
history (see finding 4).

### 2. Suspension never updates Scheduler status — systemic, not HITL-specific

Checked both suspension primitives that exist today:

- `ctx.sleep_until_signal()` (`agents/runtime/context.py:313`) — only calls
  `self._log("run.suspended", ...)` (an EventLog write) then
  `self._signal_bus.wait_for_signal(...)`. **Never touches the scheduler.**
- `InMemorySupervisor.join()` (`agents/runtime/backends/_supervisor.py:137`)
  — literally `await asyncio.Event().wait()`. **Also never touches the
  scheduler.**

But the `Supervisor` kernel contract explicitly promises otherwise:
*"The caller's run transitions to SUSPENDED and the Scheduler releases its
lease"* (`kernel/runtime/supervisor.py:114`). **This promise is broken by
both concrete implementations that exist.**

**Consequence, traced to the actual failure path:** `PostgresScheduler
.reclaim_orphans(all_running=True)` — called at every monolith startup since
a fresh process owns no leases — matches `WHERE status = 'running'` and
requeues every such row as `'pending'`. Because suspension never changed the
status away from `'running'`, this can't distinguish "legitimately waiting on
a human/child/timer" from "genuinely crashed." **It requeues both, for every
suspension type**: `ask_human`, tool approval, and any subagent that's
`ctx.spawn()`'d and `ctx.join()`'d.

The lease is kept from expiring naturally by a 15-second heartbeat task
(`worker.py`, `_heartbeat()`) — so this specific failure mode requires an
actual process restart, not just a long wait. But a monolith restart while
*any* run in the system is suspended will hit it.

### 3. `Checkpoint` is referenced by 3 docstrings, implemented nowhere

```
grep -rn "class Checkpoint" src/substrate/
```
returns **zero matches**. Yet:
- `kernel/core/errors.py:41` — `AgentCrashError`'s own docstring: *"the
  orchestrator... re-dispatches the agent... resuming from the last
  Checkpoint (see `kernel/agent.py`)"*
- `kernel/runtime/log_entry.py:8-10` — *"`Checkpoint` (in `kernel/agent.py`)
  is demoted to a log-compaction snapshot"*
- `kernel/runtime/agent.py:9` — same reference

The file path cited (`kernel/agent.py`) doesn't even exist — it's `kernel/agent/`,
a package, whose four files (`context.py`, `middleware.py`,
`runtime_context.py`, `supervision.py`) contain no `Checkpoint` class. This
isn't a stub or a `NotImplementedError` — the concept referenced by three
separate docstrings simply was never written.

### 4. Coarse-grained journaling loses HITL state across a crash — traced end to end

This is the concrete, reproducible bug that finding #1's "fortunate
coincidence" doesn't cover.

`ctx.tool()` (`agents/runtime/context.py:456`) computes an `effect_id`,
checks the Journal, and on a miss:
```python
result = await self._tool_invoker.invoke(call, session=..., ctx=self)  # ← suspension happens INSIDE here
await self._journal.record(EffectResult(effect_id=effect_id, ...))      # ← only recorded AFTER
```
For `ask_human`, `AskHumanTool.execute()` suspends (via
`ctx.sleep_until_signal`) **inside** that `invoke()` call — meaning the whole
tool call, suspension included, is treated as one atomic effect that isn't
recorded until it fully completes.

**Failure trace:**
1. Process crashes while suspended (human hasn't answered yet). The effect
   was never recorded — Journal has no entry for this `effect_id`.
2. `reclaim_orphans` requeues the run (per finding #2). A fresh process calls
   `agent.run()`.
3. Replay reaches the same `ctx.tool("ask_human", ...)` call. Journal lookup
   **misses** (nothing was ever recorded). `AskHumanTool.execute()` runs
   again from scratch.
4. `HumanInputRequest.request_id: str = Field(default_factory=lambda:
   str(uuid4()))` — a **brand-new** UUID is generated. The card the user was
   looking at (with the old `request_id`) is now permanently orphaned:
   clicking it 404s, because the new process's `WebHITLBridge._signal_requests`
   (in-memory, wiped on restart) never registered the old id.
5. Worse case: if the crash happens **after** the human already answered but
   **before** `Journal.record()` executed, their answer is silently
   discarded the same way — replay re-asks, from zero, a question that was
   already answered.

This is not a hypothetical — it's a direct trace through code that exists
today, using the crash-timing gap that finding #2 creates.

### 5. Zero test coverage of the actual event-sourcing/replay contract

`tests/architecture/test_kernel_invariants.py` — read in full. It checks:
LOC ceiling, file-count ceiling, flat directory layout, no upward imports, no
vendor strings, and 5 basic Pydantic serialization round-trips
(`Message`, `Event`, unknown/invalid content blocks, custom payload types).

**None of these test the property the framework's entire value proposition
rests on**: that `EventLog` concurrency fencing actually rejects a stale
append, that `Journal` at-most-once actually skips re-execution on a
Journal hit, that `Effect.make_id` is actually deterministic across two
calls with identical args, or — the one that matters most — that a
simulated crash-and-replay of a run produces consistent state without
double-executing a side effect. For a framework whose pitch is "safe retry
for enterprises," this is the single area most needing test coverage, and it
currently has none.

### 6. Durable backends: 2 of 6 still Stage 0 only

`SignalBus` and `Supervisor` have no Postgres/Redis implementation —
confirmed via `find src/substrate -iname "*signal*"` (only
`agents/runtime/backends/_signal_bus.py`, in-memory) and no `Postgres` /
`Redis` prefixed Supervisor class exists anywhere. This is the concrete
manifestation of finding #2 — even if suspension *did* correctly update
scheduler status, the SignalBus itself still can't survive a process
restart (its `_waiters` dict is a plain Python dict in process memory).

### 7. Kernel size: 5086 / 6000 LOC (85% of ceiling)

Not urgent — but worth knowing before the next feature addition trips
`test_kernel_loc_ceiling` and forces an unplanned "what do we split out"
conversation mid-task.

## What needs to be done — prioritized

Ordering rationale: fix the thing that's silently losing/duplicating state
today, before adding tests for it (tests need a fixed target), before adding
new durable backends (which would otherwise just create more Stage-0-only
surface area with the same untested gap).

1. **Make every suspension primitive update Scheduler status.**
   `sleep_until_signal`, `sleep_until`, and `Supervisor.join()` should all
   transition the run to a status `reclaim_orphans` can recognize as
   legitimately-waiting, not crashed. This single fix closes the orphan-reclaim
   hole for *all* suspension types at once (HITL, timers, subagent joins) —
   it's the highest-leverage fix here.

2. **Fix the crash-window in `ctx.tool()` around suspending effects.**
   Either: (a) make the Journal record happen *before* re-entering the part
   of the call that can suspend (so a resumed run finds the in-flight state
   rather than re-executing), or (b) make suspending tools generate
   deterministic, replay-stable identifiers (e.g. derive `request_id` from
   `effect_id` instead of a fresh `uuid4()`) so even a full re-execution
   produces the *same* card id and a stale-but-consistent request can still
   be resolved. (b) is likely the smaller, safer change.

3. **Add crash/replay tests to `test_kernel_invariants.py` or a sibling
   file.** At minimum: a test that fires two concurrent `append()`s with the
   same `expected_seq` and asserts one raises `ConcurrentAppendError`; a test
   that calls the same journaled effect twice and asserts the second call
   never re-executes the side effect; and an integration-level test that
   suspends a run, kills the "process" (drops the in-memory state), replays,
   and asserts no duplicate side effect occurred. Do this *after* #1 and #2
   land, so the tests assert the fixed behavior, not the current gap.

4. **Build a durable `SignalBus`** (Redis pub/sub, matching the documented
   Stage 1 direction in `kernel/runtime/wakeup.py:68`). Without this, #1
   alone isn't sufficient — the scheduler would correctly know a run is
   suspended, but the signal itself would still be lost on restart since
   `InMemorySignalBus._waiters` doesn't persist.

5. **Either implement `Checkpoint` or remove the dangling references.**
   Three docstrings currently describe behavior that can't happen. Pick one:
   build the log-compaction snapshot mechanism they describe (only worth it
   once run logs get long enough that full replay is expensive), or edit the
   docstrings to stop promising something that doesn't exist. Leaving it as
   the false middle ground actively misleads anyone reading the kernel to
   understand it.

6. **Build a durable `Supervisor`** (Postgres-backed run registry, per its
   own Stage 1 note). Lower urgency than `SignalBus` since subagent
   orchestration is less exposed to user-visible crash windows than HITL
   is, but the same fundamental gap applies.
