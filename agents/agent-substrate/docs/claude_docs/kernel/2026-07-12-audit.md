# Kernel Audit — 2026-07-12

## Since the last audit (2026-07-02)

The first audit found the kernel's *durable-runtime* contracts sound but the
concrete implementation not yet delivering true stateless replay (no
`fold`/replay function, suspension never updating Scheduler status, coarse
journaling losing HITL answers on crash, `Checkpoint` referenced but
nonexistent). All of that has since shipped — the entire Phase 0-5
remediation program (`../roadmap.md`) and last session's v1 remediation
program landed the event-sourced runtime this audit's evidence below
confirms is genuinely solid: `EventLog`/`Scheduler`/`Inbox`/`Supervisor`/
`SignalBus`/`Effect`/`EffectResult` are heavily used, battle-tested by both
programs, and not touched by this audit.

This audit is a different kind of pass: not "does the durable-runtime
contract work," but "is every kernel export honest — does something real
consume it, or is it aspirational scaffolding that never got finished."
Triggered directly by the user, after the v1 remediation program, asking for
a ground-up rethink of the kernel foundation specifically because rot kept
recurring above it (steps-table drift, Journal duplication, a dependency
audit blind spot, three parallel HITL abstractions) and the working
hypothesis was that kernel itself wasn't being curated rigorously enough to
prevent that.

## Method

Every symbol in `kernel/__init__.py`'s `__all__` (130 names) was checked
against real consumption across `agents/`, `capabilities/`, `fabric/`,
`serving/`, `infrastructure/`, `integrations/`, and `tests/` — not import
counts, but tracing whether the real call path uses the contract or bypasses
it. A symbol with grep hits only inside kernel's own re-export chain
(`kernel/__init__.py` → `kernel/<sub>/__init__.py` → definition file) counts
as zero real consumers. Every finding below is a `grep`/trace, not a
docstring claim — several docstrings turned out to describe intended
behavior that was never actually built (see Findings).

## Findings

### Tier A — confirmed dead, deleted

Zero real consumers anywhere, including tests, beyond kernel's own exports:

- `AgentNotFoundError`, `HandlerError` (`kernel/core/errors.py`) — never
  raised or caught.
- `SpawnDenied` (`kernel/core/errors.py`) — its own docstring claimed
  `SpawnTracker` raises it on a denied spawn; the real implementation
  (`agents/supervision/budget.py`) raises `BudgetExhaustedError` instead.
- `ControlPayload`, `ProgressPayload`, `register_payload_type`
  (`kernel/messaging/message.py`) — registered payload kinds/extension hook
  nothing ever constructs or calls.
- `Event`, `EventHandler`, `EventPublisher`, `EventSubscriber`
  (`kernel/messaging/events.py`, deleted entirely) — module docstring
  claimed this is "shared by in-process and distributed event buses," but
  the real event bus (`integrations/events/envelope.py::EventEnvelope`) is
  an independently-defined type. Its `from_kernel_event()`/
  `to_kernel_event()` bridge methods — built specifically to connect the
  two — were never called anywhere either.
- `CONTENT_BLOCK_TYPES`, `register_block_type`, `ThinkingBlock`,
  `UIResourceBlock` (`kernel/core/content.py`) — an extension mechanism with
  zero registrations, and two content-block variants wired into the
  discriminated union but never produced by any LLM client or tool.
  `UIResourceBlock` in particular: the real MCP-app interactive-UI feature
  (`serving/monolith/routes/mcp_apps.py`) uses an ad-hoc dict/
  `_meta.ui.resourceUri` mechanism instead — never this kernel type.
- `FunctionSpec`, `ProviderSpec`, `ToolSpec`, `spec_of()`, `ToolExecution`
  (`kernel/tools/tools.py`) — built to replace "ad-hoc dict soup in
  encoders" (the function's own docstring), but the one real consumer that
  soup lives in (`agents/tools/toolbox.py::Toolbox.schemas()`) was never
  migrated to call it — it still hand-builds dicts and reads
  `tool.provider_specs` directly. `ToolExecution` (LOCAL/PROVIDER/
  PROVIDER_DEFINED) claimed to drive provider routing; the real dispatch
  uses `is_hosted_tool()`/`is_provider_defined_tool()` TypeGuards instead.

Kernel shrank from 5295 to ~4840 LOC across the full audit (41 → 40 files),
well under the 6000 LOC / 45 file ceiling in
`tests/architecture/test_kernel_invariants.py`.

### Tier B — half-wired, fixed

- `Supervision.execution_budget` (`kernel/agent/supervision.py`) genuinely
  propagated through `ctx.spawn()` → `Supervision.spawn_child()` →
  `RunMeta.supervision` — verified end to end — but nothing ever read
  `meta.supervision.execution_budget` to build an enforced
  `ExecutionTracker` for the spawned child. `grep -rn "ExecutionTracker("`
  across the whole codebase returned zero constructions outside tests. A
  spawned child got whatever `ExecutionTracker` its `ReActAgent` happened to
  be built with (in practice, none), regardless of what budget the kernel
  type said it should inherit.

  Fixed in `ReActAgent._resolve_execution_budget()`
  (`agents/core/react.py`): builds the effective tracker fresh per `run()`
  call — inherited `Supervision.execution_budget` takes priority when
  present, falling back to the constructor default otherwise. Built fresh
  rather than cached on `self` because an `Agent` instance is registered
  once and reused across every run of its `agent_id`
  (`Runtime.register()`) — a shared, mutating tracker on `self` would let
  concurrent runs of the same registered agent corrupt each other's usage
  counters. New test:
  `test_spawned_child_inherits_execution_budget_from_supervision`
  (`tests/agents/test_budgets.py`) — a child spawned under a tight budget,
  with no `execution_budget` on its own constructor, still hits
  `BudgetExhaustedError`.

### Tier C — the headline finding: tool-approval had zero live wiring

Three independently-built approval abstractions, traced end to end:

1. `kernel/tools/approval.py`'s `ApprovalHandler` Protocol — consumed for
   real by `agents/tools/invoker.py::ToolInvoker` at dispatch time, and
   `agents/runtime/worker.py::_build_tool_invoker` even built an adapter for
   bare-callback handlers. Genuinely live machinery. But
   `ReActAgent(approval_handler=...)` was never actually passed a value
   anywhere in the real construction path — `grep -rn "approval_handler="
   agents/factory.py infrastructure/serving_factory.py` returned nothing.
2. `capabilities/tools/tool_approval.py` — an entirely separate
   `ToolApprovalRequest`/`Response`/`Handler` family (pydantic, richer:
   supported `MODIFY`, which kernel's `ApprovalDecision` didn't).
3. `serving/monolith/sse/bridge.py::WebHITLBridge` built a real
   `CallbackApprovalHandler` (from #2) wired to SSE with actual `hitl_mode`
   branching logic (`fire_and_continue`/`continue_on_timeout`/`blocking`).
   Its `approval_handler` property was read from **nowhere** except its own
   definition — the module's own usage-example docstring showed
   `ReActAgent(..., tool_approval_handler=bridge.approval_handler, ...)`, a
   parameter name that doesn't exist on `ReActAgent` (the real one is
   `approval_handler`).

**Net effect verified by tracing the full call graph:** a CRITICAL-risk tool
call was not gated on human approval anywhere in the live monolith. The
prior roadmap's "Future-based tool-approval → signal migration... explicitly
deferred" entry undersold this — it wasn't "using Futures instead of
signals," it was "not connected to a running agent at all."

**Resolved** (user confirmed direction): consolidated on the kernel
Protocol (#1). Added `ApprovalDecision.MODIFIED` + a new `ApprovalResult`
wrapper (`decision` + `modified_args`) to kernel so it covers everything
`ToolApprovalResponse.MODIFY` did; deleted `capabilities/tools/
tool_approval.py` entirely (including `CLIApprovalHandler`, which turned out
to also be dead — never wired to the interactive console either) and
`WebHITLBridge`'s approval half; added `serving/monolith/sse/approval.py::
SSEApprovalHandler` implementing the kernel Protocol directly against the
bridge's existing Future/queue mechanism; wired it through
`build_agent_for_thread(bridge=...)` into the real chat construction path.
New end-to-end test
(`tests/infrastructure/test_serving_factory_approval.py`) goes through
`build_agent_for_thread()` itself — not a hand-built
`ReActAgent(approval_handler=...)` — proving the wiring is reachable from a
real chat request, the exact gap that let this go unnoticed.

### Tier D — root cause note

The tool-approval triplication is the same shape of problem as three prior
findings in `../roadmap.md`'s "Recently shipped" (the `_cosine_similarity`
triplication, `EventEnvelope` vs kernel `Event`, `HITLResponse.action`
Literal misalignment between monolith and microservices): a domain concept
gets a second (or third) independent implementation at a different layer,
and nothing catches the drift because each implementation "works" in
isolation — the disconnect only shows up when you trace the real call graph
end to end, which a unit test of any single layer can't do. Worth watching
for specifically when adding a new capability that has an obvious kernel
Protocol nearby: check whether the Protocol is actually *reachable* from the
real serving path, not just whether a concrete class satisfies it.

`serving/shared/contracts/human_gate.py::HITLApprovalRequest` (the
microservices equivalent) was not touched — out of scope for this pass, but
now that the monolith's shape is settled (kernel `ApprovalRequest`/
`ApprovalResult`), it's the next thing to check for the same drift if
`human_gate`'s approval flow is ever revisited.

## Incidental finding: a real, reproducible ~35s test "hang"

While verifying Tier A/B, `tests/agents/test_supervision_v2.py::
test_crash_records_agent_crashed_status` appeared to hang under any
reasonable test timeout. Root cause: it submits with the default
`max_retries=3`, and a bare `RuntimeError` is unclassified — therefore
retryable by default (see `worker.py`'s exception handler). The `BombAgent`
raises the same way on every attempt, so the run backs off and retries 3
times (5s/10s/20s exponential backoff) before finally recording
`run.failed`. Confirmed via `git stash` that this reproduces identically on
the pre-kernel-audit tree — pre-existing, not a regression from this
session, just never noticed because nobody ran this one test in isolation
with a short timeout before. Fixed with `max_retries=0`, matching the
existing pattern in `test_hooks.py::test_run_end_fires_even_on_agent_crash`
for the same scenario.

Nothing further identified in this pass — Tiers A/B/C are the full extent of
kernel rot found. The `human_gate` approval-contract drift noted in Tier D
is the one flagged-but-not-acted-on item; otherwise the kernel is now
believed clean: every export has a traced real consumer, or has been
deleted.

**Re-verified 2026-07-12, later same day:** a follow-up question ("how does
dynamic/lazy tool-description loading work without `DeferredTool`?") surfaced
one more Tier-A-shaped miss: `defer_loading` (`kernel/tools/tools.py`'s `Tool`
Protocol) was never actually threaded from a `Tool` object into a wire dict on
*any* provider path — checked `_tools_from_options` in all three of
`openai_client.py`/`gemini_client.py`/`anthropic_client.py`; none of them
carry it through. `Toolbox.schemas()`/`.deferred_schemas()`/`.schema_for()`
(`agents/tools/toolbox.py`), the only code that would have consulted it, had
zero real callers — only exercised by a test of themselves
(`tests/kernel/test_tools.py`). Same root cause as the `ToolSpec`/`spec_of`
finding above: scaffolding for a feature that was superseded by
`ToolSearchTool`/`SkillTool`'s roster-in-context pattern before it was ever
wired up. Deleted `defer_loading` from the `Tool` Protocol docstring, deleted
the three dead `Toolbox` methods, and stripped the now-unreachable
`defer_loading` branch out of `integrations/llm/encoders/openai.py`'s
`encode_tools()`. This was initially mis-assessed in conversation as "working
on the OpenAI Responses-API path" — corrected after tracing
`_tools_from_options` directly rather than trusting the earlier claim.
